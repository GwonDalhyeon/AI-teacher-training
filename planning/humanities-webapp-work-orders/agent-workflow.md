# 문과 계열 웹앱 병렬 구현 운영 지시서

이 문서는 `도시의 미래탐구`, `법과 사회` 웹앱 후보 6개를 에이전트로 병렬 구현할 때 사용하는 운영 지시서다. 목표는 빠른 구현이 아니라, **웹앱이 학습목표를 더 효과적으로 달성하는지 검토한 뒤 구현하는 것**이다.

## 1. 운영 원칙

- 웹앱은 에듀테크 사용 자체가 목적이 아니다.
- 웹앱은 교사가 말, 판서, 활동지, 단순 교구로 구성하기 어려운 관계·변화·충돌·조건부 판단을 보여 주어야 한다.
- 구현 전에 수업효과 검토 에이전트가 후보 6개를 평가하고, 상위 3개를 먼저 선택한다.
- 상위 3개를 구현한 뒤 만족스러우면 나머지 3개를 같은 절차로 구현한다.
- 구현 에이전트는 자기 앱 폴더만 수정한다.
- 공통 파일은 조율 에이전트만 수정한다.

## 2. 에이전트 역할

### 조율 에이전트

책임:

- 작업 범위와 파일 소유권을 나눈다.
- 구현 에이전트가 공통 파일을 수정하지 않도록 제한한다.
- 수업효과 검토 에이전트의 판정을 구현 순서에 반영한다.
- 구현 완료 후 `webapps/index.html`, `webapps/README.md`, `planning/status.md` 등 공통 파일을 통합 수정한다.
- 최종 검증 결과를 정리한다.

수정 가능 파일:

- `webapps/index.html`
- `webapps/README.md`
- `planning/status.md`
- 필요 시 `planning/web-apps.md`

### 수업효과 검토 에이전트

책임:

- 후보 웹앱이 학습목표 달성에 실제로 도움이 되는지 판단한다.
- 아하포인트가 약하거나 정보 나열형으로 흐를 위험이 있으면 수정 요구를 낸다.
- 구현 전 후보 6개를 엄격히 평가해 상위 3개를 선택한다.
- 구현 후 실제 앱을 다시 검토하고 수정 요청 또는 통과 판정을 낸다.

권한:

- 구현 전 `보류` 판정을 내릴 수 있다.
- 구현 전 작업지시서 수정을 요구할 수 있다.
- 구현 후 앱이 학습목표를 충분히 살리지 못하면 재작업을 요구할 수 있다.
- 단, 코드 취향이나 장식적 디자인 선호로 구현을 막지 않는다. 판단 근거는 학습목표, 아하포인트, 수업 시연성으로 제한한다.

### 구현 에이전트

책임:

- 배정받은 웹앱 하나만 구현한다.
- 해당 앱의 작업지시서를 따른다.
- 학습목표, 아하포인트, 시연 흐름을 우선 구현한다.
- 완료 후 구현한 상호작용, 미흡한 점, 수정 파일을 보고한다.

수정 가능 파일:

- `webapps/{assigned-folder}/index.html`

수정 금지 파일:

- `webapps/index.html`
- `webapps/README.md`
- `planning/status.md`
- `planning/web-apps.md`
- 다른 앱 폴더의 파일

## 3. 후보 6개

도시의 미래탐구:

- `city-smart-city-balance.md`
- `city-heat-vulnerability-map.md`
- `city-budget-for-all.md`

법과 사회:

- `law-contract-validity-checker.md`
- `law-inheritance-family-tree.md`
- `law-youth-rights-age-lab.md`

## 4. 구현 순서

1. 조율 에이전트가 후보 6개와 파일 소유권을 확인한다.
2. 수업효과 검토 에이전트가 후보 6개를 사전 평가한다.
3. 수업효과 검토 에이전트가 상위 3개를 선택하고, 각 후보의 필수 보완점을 제시한다.
4. 조율 에이전트가 상위 3개 구현 에이전트를 병렬로 배정한다.
5. 구현 에이전트 3명이 각자 자기 앱 폴더의 `index.html`만 만든다.
6. 수업효과 검토 에이전트가 구현된 3개 앱을 사후 평가한다.
7. 조율 에이전트가 필요한 수정 작업을 같은 파일 소유권 기준으로 배정한다.
8. 상위 3개가 통과하면 나머지 3개를 같은 방식으로 진행한다.
9. 조율 에이전트가 목록 페이지와 상태 문서를 마지막에 통합한다.

## 5. 엄격 판정 기준

| 등급 | 기준 | 처리 |
|------|------|------|
| A | 조작 전후 변화가 개념 이해로 바로 이어지고, 교사가 설명하기 어려운 구조를 보여 준다. 1-3분 시연에 적합하다. | 우선 구현 |
| B | 학습목표와 연결되지만 아하포인트, 조작 구조, 시연 흐름 중 하나가 약하다. | 보완 후 구현 |
| C | 정보 카드, 퀴즈, 설명문 중심이라 웹앱이어야 할 이유가 약하다. | 구현하지 않음 |
| 보류 | 교과 개념 오류, 법적 민감성, 사회적 편향 위험이 있다. | 수정 전 구현 금지 |

상위 3개는 단순 평균 점수가 아니라 다음 조건을 모두 고려해 고른다.

- 학습목표 직접성
- 아하포인트의 선명함
- 교사가 일반 수업에서 구성하기 어려운 정도
- 1-3분 시연 가능성
- 상호작용의 의미
- 개념 오류와 민감성 위험
- 구현 난이도 대비 교육 효과

## 6. 질문 풀

수업효과 검토 에이전트는 모든 질문을 기계적으로 적용하지 않는다. 후보 성격에 맞게 아래 질문 중 필요한 것을 골라 묻고, 필요하면 표현을 바꾼다.

### 학습목표 연결

- 이 앱의 핵심 학습목표는 무엇인가?
- 앱의 조작 결과가 학습목표와 직접 연결되는가?
- 교과서 내용을 단순 복제하지 않고 개념 이해 장면으로 바꾸었는가?
- 학생이 앱을 본 뒤 말할 수 있어야 하는 한 문장은 무엇인가?

### 아하포인트

- 학생의 기존 직관이나 단순 생각은 무엇인가?
- 그 직관이 어떤 조작에서 흔들리는가?
- 결과 변화가 즉시 보이는가?
- 아하포인트가 텍스트 설명이 아니라 화면 변화로 먼저 드러나는가?

### 교사의 설명 부담

- 교사가 말이나 판서로 설명하기 어려운 관계가 있는가?
- 활동지나 교구로 만들기 번거로운 요소를 웹앱이 대신하는가?
- 정지된 그림보다 웹앱이 더 잘 보여 주는 변화가 있는가?
- 수업 중 1-3분 시연으로 도입, 전환, 정리에 쓸 수 있는가?

### 상호작용의 의미

- 학생이나 교사가 바꾸는 값이 개념적으로 중요한가?
- 버튼, 슬라이더, 카드 선택이 단순 장식이 아닌가?
- 조작을 바꾸면 결과가 충분히 다르게 나타나는가?
- 원인과 결과가 같은 화면에서 연결되어 보이는가?

### 위험 요소

- 정보 나열형 대시보드로 흐를 위험이 있는가?
- 퀴즈나 정답 확인 앱으로 축소될 위험이 있는가?
- 법 관련 앱이 실제 법률 상담처럼 보일 위험이 있는가?
- 도시·사회 주제가 특정 집단을 고정관념적으로 묘사할 위험이 있는가?
- 지표가 너무 많아 핵심 개념이 흐려질 위험이 있는가?

### 구현 우선순위

- 이 앱은 상위 3개에 들어갈 만큼 시연 효과가 큰가?
- 구현 난이도에 비해 교육 효과가 충분한가?
- 첫 화면 10초 안에 "무엇을 바꾸면 무엇이 달라지는지" 보이는가?
- 앱이 없어도 말로 충분히 설명되는 내용은 아닌가?

## 7. 구현 전 리뷰 형식

```text
후보명:
작업지시서:
판정: A / B / C / 보류

핵심 학습목표:
학생이 조작으로 발견해야 할 것:
아하포인트:
교사가 설명하기 어려운 지점:
웹앱이어야 하는 이유:
필수 상호작용:
줄여도 되는 요소:
위험 요소:
수정 요구:
상위 3개 포함 여부:
```

## 8. 구현 후 리뷰 형식

```text
앱 이름:
파일:
판정: 통과 / 수정 후 통과 / 재작업 / 보류

학습목표 적합성:
아하포인트 선명도:
개념 직관화:
교사 설명 부담 감소:
학생 조작의 의미:
1-3분 시연 가능성:
텍스트 과다 여부:
민감성·오해 위험:
수정 요청:
최종 의견:
```

판정 기준:

- `통과`: 목록 페이지에 올릴 수 있다.
- `수정 후 통과`: 작은 문구, 지표, 배치 수정 후 통합 가능하다.
- `재작업`: 상호작용 또는 핵심 구조가 학습목표를 살리지 못한다.
- `보류`: 개념 오류나 민감성 문제가 있어 공개 시연하면 안 된다.

## 9. 구현 에이전트 공통 프롬프트

```text
너는 하나의 웹앱만 구현한다.
수정 가능 파일은 webapps/{folder}/index.html 하나뿐이다.
다른 에이전트도 동시에 작업 중이므로 공통 파일과 다른 앱 폴더는 수정하지 않는다.

단일 HTML, Tailwind CSS CDN, vanilla JavaScript만 사용한다.
백엔드, 빌드 도구, 외부 API, 패키지 설치를 사용하지 않는다.
화면에 보이는 문구는 한글로 쓴다.

작업지시서의 핵심 의도, 아하 모먼트, 시연 흐름을 우선 구현한다.
퀴즈형 앱이 아니라 조건을 바꾸면 결과가 달라지는 시뮬레이션형 앱으로 만든다.
첫 화면 10초 안에 무엇을 조작하면 무엇이 달라지는지 보여야 한다.

완료 후 다음을 보고한다.
- 수정 파일
- 구현한 상호작용
- 학습목표를 살린 방식
- 미흡한 점 또는 후속 검토 필요 사항
```

법 관련 앱에는 아래 문장을 추가한다.

```text
이 앱은 법률 상담 도구처럼 보이면 안 된다.
화면 하단에 "수업용 단순화 예시입니다. 실제 기준은 최신 법령을 확인하세요."라는 안내를 넣는다.
결과 문장은 단정하지 말고 "이 조건을 가정하면"처럼 수업용 조건 판단으로 표현한다.
```

## 10. 통합 전 체크리스트

- 수업효과 검토 에이전트가 `통과` 또는 `수정 후 통과` 판정을 냈는가?
- 구현 에이전트가 자기 앱 폴더만 수정했는가?
- 공통 파일 수정은 조율 에이전트가 마지막에만 했는가?
- 앱별 제목, 핵심 질문, 조작 영역, 결과 영역이 한 화면에서 연결되는가?
- 모바일 화면에서 버튼과 결과가 겹치지 않는가?
- `git diff --check`를 통과했는가?
- 가능하면 로컬 브라우저에서 주요 버튼을 눌러 보았는가?
